# 내부 아키텍처 (커밋 금지)

이 문서는 **내부용**이며 Git에 포함되지 않도록 의도적으로 제외되어 있습니다. 현재 아키텍처, 데이터 모델, 주요 요청 흐름, 보안 통제를 **종합적으로** 정리합니다.

## 1) 상위 아키텍처

### 구성 요소

- **웹 클라이언트**
  - 서버 렌더링(SSR) 뷰: `views/`의 EJS 템플릿
  - 글/댓글/비밀번호 재설정 등은 fetch/AJAX로 요청
  - 실시간 채팅은 Socket.io 클라이언트 사용
- **API / Web 서버**
  - `index.js`의 Node.js + Express 애플리케이션
  - SSR 렌더링 + JSON 엔드포인트 혼합
  - 인증: Passport LocalStrategy + `express-session`
  - CSRF 방어: 세션 기반 토큰(`ensureCsrfToken` / `requireCsrf`)
  - 레이트 리밋: 인증/메일 관련 엔드포인트에 적용(express-rate-limit)
- **DB**
  - MongoDB (`mongodb` 드라이버로 직접 접근; Mongoose 의존성은 있으나 주요 흐름은 드라이버 사용)
- **외부 서비스**
  - 비밀번호 재설정 인증코드 발송용 SMTP(Nodemailer)

### 데이터 흐름(개요)

1. 브라우저가 페이지 요청(EJS SSR) → Express가 뷰 렌더링
2. 폼 제출 또는 fetch/AJAX 요청 → Express 라우트 핸들러
3. Express가 MongoDB 컬렉션 읽기/쓰기
4. 실시간 채팅은 Socket.io, 메시지 스트리밍은 SSE 엔드포인트로 처리

## 2) 실행 환경 & 배포

### 로컬 실행(호스트)

- MongoDB를 Docker로 실행한 뒤, 필요 시 `DB_URL`을 `localhost`로 설정
- 서버 실행: `node index.js`

### Docker Compose (demo/dev)

- MongoDB 컨테이너: 호스트 `27018` → 컨테이너 `27017`
- App 컨테이너: 호스트 `3002` → 컨테이너 `3000`

## 3) 주요 라우트

### 공개 페이지(비로그인)

- `GET /` → 로그인 페이지
- `GET /login` → 로그인 페이지
- `GET /signup` → 회원가입 페이지
- `GET /reset-password` → 비밀번호 재설정 UI(AJAX)
- `GET /findid` → 아이디 찾기 UI(AJAX)

### 인증/계정

- `POST /signup` (CSRF + authLimiter)
- `POST /login` (CSRF + authLimiter)
- `GET /logout`
- `POST /findid` (CSRF + authLimiter)

### 비밀번호 재설정(메일)

- `POST /reset-password` (CSRF + emailLimiter): 인증코드 생성/메일 발송
- `POST /verify-code` (CSRF + authLimiter): 메모리 Map에 저장된 코드 검증
- `POST /reset-password-new` (CSRF + authLimiter): 비밀번호 해시 업데이트

### 게시판

- `GET /list` (로그인 필요): 글 목록
- `GET /detail/:id` (로그인 필요): 글 상세 + 댓글
- `GET /write` (로그인 필요): 작성 화면
- `POST /add` (로그인 + CSRF): 글 생성 (`counter`로 다음 `_id` 할당)

### 수정/삭제 권한

- `GET /edit/:id` (로그인 필요): 작성자만 접근
- `POST /edit/:id` (로그인 + CSRF): 작성자만 업데이트
- `POST /delete` (로그인 + CSRF): 작성자만 삭제(HTML form)
- `DELETE /delete` (로그인 + CSRF): 작성자만 삭제(AJAX)

### 댓글

- `POST /comment/add` (CSRF)
- `POST /comment/reply` (CSRF)

### 업로드

- `GET /upload` (로그인 필요)
- `POST /upload` (로그인 + CSRF)
  - Multer 제한: 최대 10개, 파일당 5MB
  - MIME 필터: `image/*`
  - 업로드 후 검증: `file-type`로 매직바이트 검사 → 이미지가 아니면 즉시 삭제
  - 저장 파일명: 랜덤화(덮어쓰기 방지)

### 실시간 메시징

- Socket.io: `io.on('connection', ...)` 기반 브로드캐스트
- SSE: `GET /message/:id` 스트리밍(Change Streams)

#### SSE를 사용한 이유

- **서버 → 클라이언트 단방향 스트리밍에 최적**: 채팅 “수신”처럼 서버가 이벤트를 계속 밀어주는 형태에 SSE가 단순하고 적합합니다.
- **구현/운영 비용이 낮음**: HTTP 기반(`text/event-stream`)이라 프록시/로드밸런서 환경에서 WebSocket보다 설정이 간단한 경우가 많습니다.
- **자동 재연결 지원**: 브라우저 `EventSource`는 네트워크 단절 시 자동 재연결을 제공해 UX가 안정적입니다.
- **권한/세션 연동이 쉬움**: 쿠키/세션 기반 인증과 자연스럽게 결합할 수 있어, 로그인 상태를 전제로 한 스트림에 사용하기 좋습니다.
- **Socket.io와 역할 분리**: Socket.io는 양방향(전송/룸/이벤트) 채팅에 쓰고, SSE는 “구독/수신 스트림”에 쓰는 식으로 책임을 나눌 수 있습니다.

> 메모: 현재 구현은 Change Streams 기반 스트리밍이므로, 운영에서 MongoDB 구성이(Replica Set 등) 필요할 수 있습니다. 단일 인스턴스에서 문제되면 폴링/Socket.io 단일화 등으로 단순화하는 것도 선택지입니다.

## 4) 데이터 모델 (MongoDB 컬렉션)

- `login`
  - `{ id, pw(bcrypt 해시), em, nm, ... }`
- `post`
  - `{ _id(int), 제목, 내용, 작성자, 작성자_id, 날짜, likes?: [userId] }`
- `comments`
  - `{ _id, postId(int), content, writer, writer_id, date, parentId? }`
- `counter`
  - `{ name: '게시물갯수', toTalPost: number }` (없으면 upsert로 자동 생성)
- `chatroom`
  - `{ title, member: [userId], date }`
- `message`
  - `{ parent, userid, content, date }`

## 5) 보안 통제(현재 상태)

- **시크릿 관리**: `.env`는 제외, `.env.example`만 제공
- **CSRF**: 상태 변경 라우트는 토큰 필수(헤더 또는 hidden input)
- **레이트 리밋**
  - 인증 관련: 15분당 20회
  - 메일 재설정: 15분당 10회
- **인가(권한)**
  - 수정/삭제: 작성자만 가능
- **업로드**
  - content-type + 매직바이트 검증 + 사이즈 제한
- **세션 쿠키**
  - `httpOnly`, `sameSite=lax`, 프로덕션에서 `secure`

## 6) 한계/후속 과제

- 인증코드 저장이 메모리 Map 기반 → 멀티 인스턴스에서는 Redis 등 공유 스토리지 필요
- 세션 스토어가 기본 메모리 → 운영 환경에서는 Redis/Mongo 세션 스토어 권장
- 글/댓글 입력값 검증 및 XSS 방어(정규화/escape/sanitize) 강화 필요

## 7) 사용 라이브러리(의존성)

> 아래는 “무엇을 쓰는지” 뿐 아니라, **왜 선택했는지(사용 이유)** 를 같이 정리합니다.

### 핵심 서버/라우팅

- **express**: HTTP 서버/라우팅 프레임워크  
  - **사용 이유**: 라우팅/미들웨어 생태계가 풍부하고, SSR(EJS) + JSON API를 한 서버에서 빠르게 구성 가능
- **body-parser**: 요청 본문 파싱(JSON 등) *(현재 코드에서는 Express 기본 파서와 함께 사용 중)*  
  - **사용 이유**: 기존 코드 기반에서 JSON 파싱을 안정적으로 처리하기 위해 사용(리팩터링 시 `express.json()`으로 통일 가능)
- **ejs**: 서버 사이드 템플릿 엔진(SSR)  
  - **사용 이유**: 별도 프론트 빌드 없이 서버에서 즉시 화면 렌더링 가능(폼 기반 페이지에 적합)
- **dotenv**: `.env` 환경 변수 로딩  
  - **사용 이유**: DB/SMTP/시크릿 등 민감 설정을 코드에서 분리하고 로컬·배포 환경에 따라 쉽게 교체
- **cookie-parser**: 쿠키 파싱  
  - **사용 이유**: 쿠키 기반 값 처리(세션/CSRF 토큰 등)에서 일관된 파싱 제공
- **connect-flash**: 플래시 메시지(리다이렉트 메시지 등)  
  - **사용 이유**: 로그인 필요/실패 등 “리다이렉트 후 1회성 메시지” UX를 간단히 구현

### 인증/세션

- **passport**, **passport-local**: 로컬 아이디/비밀번호 인증  
  - **사용 이유**: 인증 플로우(검증/세션 연동)를 표준 패턴으로 구성하고, 추후 OAuth 등 확장이 용이
- **express-session**: 세션 관리(쿠키 기반 세션 ID)  
  - **사용 이유**: 로그인 상태 유지/권한 체크를 서버 세션 기반으로 단순화  
  - **메모**: 운영 환경에서는 메모리 스토어 대신 Redis/Mongo 세션 스토어 권장
- **bcrypt**: 비밀번호 해시/검증  
  - **사용 이유**: 비밀번호를 안전하게 저장(해시 + salt)하고 검증하는 업계 표준 방식

### DB

- **mongodb**: MongoDB 드라이버(주요 데이터 접근)  
  - **사용 이유**: 컬렉션/쿼리를 직접 제어할 수 있고, 단순 CRUD 구조에서 오버헤드 없이 빠르게 개발 가능
- **mongoose**: MongoDB ODM *(의존성에 포함되어 있으나, 현재 주요 흐름은 `mongodb` 드라이버 사용)*  
  - **사용 이유**: 스키마/검증/모델 기반 개발을 원할 때 선택 가능(현재는 미사용에 가깝다면 제거 고려)

### 실시간/메시징

- **socket.io**: WebSocket 기반 실시간 통신(채팅)  
  - **사용 이유**: 브라우저 호환과 재연결/룸/이벤트 모델이 편리하며, 실시간 채팅 구현 난이도를 크게 낮춤

### 파일 업로드/검증

- **multer**: 멀티파트 파일 업로드 처리  
  - **사용 이유**: Express에서 multipart/form-data 업로드를 표준적으로 처리(파일 제한/스토리지 커스터마이징 가능)
- **file-type**: 매직바이트 기반 파일 타입 식별(업로드 후 이미지 검증)  
  - **사용 이유**: 확장자/요청 MIME 위장 공격을 보완하기 위해, 실제 파일 헤더로 “진짜 이미지인지” 확인
- **minimatch**: 패턴 매칭 유틸(프로젝트 의존성에 포함)  
  - **사용 이유**: 직접 사용하지 않더라도 일부 의존성에서 내부적으로 사용(필요 시 의존 트리로 확인)

### 메일

- **nodemailer**: SMTP 기반 이메일 전송(비밀번호 재설정 인증코드)  
  - **사용 이유**: SMTP 기반 메일 전송을 표준적으로 지원하고, 다양한 메일 서버 설정을 환경변수로 분리 가능

### 보안/트래픽 제어

- **express-rate-limit**: 로그인/메일 등 민감 엔드포인트 레이트 리밋  
  - **사용 이유**: 브루트포스/메일 폭탄 같은 남용을 최소 비용으로 완화(엔드포인트별 제한 적용 가능)

### 개발 편의(운영에는 비권장)

- **nodemon**: 개발 중 자동 재시작 도구(운영에는 보통 사용하지 않음)  
  - **사용 이유**: 코드 변경 시 서버 자동 재시작으로 개발 효율 향상(운영은 PM2/systemd/Docker 재배포 권장)

### 주의

- **node.js (0.0.1-security)**: 실제 런타임 Node.js와 무관한 “placeholder” 패키지입니다.  
  - **사용 이유**: 일반적으로 필요하지 않으며, 과거 의존성/오타로 들어오는 경우가 많음 → **제거 권장**
